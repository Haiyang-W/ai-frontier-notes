# MiMo V2.6 解读：Scaling RL Towards Self-Improvement

---

## Take Home Message

MiMo V2.6 这份报告主要回答一个问题：**怎样通过大规模 RL，让模型更可靠地完成需要多轮操作的真实任务？** 作者同时扩大训练规模、任务环境和评价投入，其中最值得关注的是：如何判断一条成功轨迹是否值得学习，以及如何让长短不一的任务稳定地参与训练。

* **大规模混合 RL 能带来持续提升。** 每步采样 1,568 道题，每题生成 16 条轨迹，总计约 2.5 万条，覆盖代码、通用工具、视觉设计等任务。RL 过程中，DeepSWE average@3 从 Pro 的 **58.4 提升到 72.6**，Flash 的 **48.7 提升到 65.7**。这说明该训练流程有效，但提升也伴随更多 token 使用，不能直接解读为同等推理成本下的收益。

* **“通过测试”之后，仍然有很多东西值得学。** 两个方案都能过测，一个修改精确，另一个靠吞异常、加冗余分支凑合，二元奖励无法区分。MiMo 用 **Groupwise Reward Synthesis（组内奖励合成，GRS）** 从多条尝试中提炼评分标准，再逐条评价实现与行为；用 **Groupwise Advantage Redistribution（组内优势重分配，GAR）** 在线比较同题方案，让质量更好的成功轨迹获得更大的正向学习权重。**关键是让模型学会更可靠的做法。** 后者的消融实验中，交互轮数更稳定，token 增长更可控，性能也能继续提升。

* **环境和验证器的质量，决定 RL 会强化什么。** 报告花了大量篇幅检查题目与测试是否一致、测试是否稳定、环境是否泄露答案。否则，模型可能学会查找现成补丁，或者利用测试漏洞拿高分。这里很有价值的一点是：**既要防止错误方案通过，也要避免正确方案被过度严格的测试误杀。**

* **模型还需要适应不同的 agent 框架。** MiMo 把工具、提示词和上下文管理做成可重组的 mini-harness，在多种配置下训练。训练过程中，未见过的 Codex、Claude Code、mini-swe-agent 上，DeepSWE 平均 Pass@1 约从 **50% 提升到 66%**，说明学到的能力能够迁移到其他执行框架。

* **长轨迹 RL 的稳定性，很大程度上取决于系统设计。** 冻结 MoE router 可以抑制本次实验中的专家负载失衡；重放路由和采样候选集，可以减少训练与推理的不一致；Sample Mixer 则根据任务耗时、接受率和当前缺额调度采样。**任务完成得快，不应该成为它在训练中占比更高的理由。** 这一点在不同数据源耗时相差 66 倍时尤其重要。

* **MixRL 先在能提供训练反馈的任务上提升能力。** 报告的大规模混合 RL 包含代码任务（68%）、通用工具使用（12%）、视觉设计（13%）、上下文遵循（3%）和网络安全（4%）。反馈既有可执行测试，也有评分标准和模型评审，因此并不限于数学、代码这类容易判断对错的题目。

* **随后用 Multi-Prefix Multi-Teacher On-Policy Distillation（多前缀、多教师在线策略蒸馏，MOPD2）合并和补充能力。** 教师有两类：在可验证任务上用 MixRL 训练的领域教师，以及在难以可靠打分的开放任务上用高质量示范训练的 SFT 教师。蒸馏时，学生可以自主完成整条轨迹，由 RL 教师逐 token 指导；也可以从教师轨迹或示范数据的某个历史节点开始，自己生成下一轮，再由对应教师指导。**这样既能合并 RL 教师的解题能力，也能利用示范教师拓展难以直接做 RL 的领域。**

## 1. 模型与训练链路：RL 为什么需要一个“适合探索”的起点

### 1.1 为什么这样设计底座：让长轨迹 RL 的每次尝试更便宜

来源：§2、Table 1、§6.4。

**Agent 做一次任务，可能要反复读代码、调用工具、检查结果，交互历史会越来越长。RL 又要让模型对同一道题尝试多次。** MiMo 每题采样 16 条轨迹，因此，单条轨迹的计算和通信成本，会被大量重复采样放大。理解这里的架构，首先要看它怎样降低这些成本。

MiMo 把两类设计组合在一起：**MoE 控制每个 token 需要调用的参数量，混合注意力控制每一层需要直接读取的上下文范围。**

* **MoE（Mixture of Experts，混合专家）：每个 token 只调用一部分专家。** 例如 Pro 总参数为 1.02T，但每个 token 的激活参数为 42B；在其 MoE 层中，每个 token 从 384 个专家里选择 8 个参与计算。这样可以保留较大的总参数容量，同时减少相对于全部参数都参与计算的开销。42B 是激活参数量，不能直接当成整模计算成本与某个 42B dense 模型完全相同。
* **SWA（Sliding Window Attention，滑动窗口注意力）：多数层只直接读取附近的上下文。** 窗口大小为 128 tokens。Pro 的 70 层主干中有 60 层使用 SWA，因此不必让每一层都对整段长历史做全局注意力。
* **GA（Global Attention，全局注意力）：用少数层连接远处的信息。** Pro 其余 10 层使用 GA，让当前位置仍能直接访问远处的历史。因此，128 是局部注意力的窗口大小，模型支持的上下文长度则达到 1M；这两个数字描述的是不同的东西。

这些设计还会影响多卡训练。长序列被分到多张 GPU 上时，一张卡可能需要从其他卡取得注意力所需的 key/value（KV）。报告 §6.4 指出，**SWA 层只需交换窗口能够覆盖的 KV，这部分通信量由窗口大小约束，而不会随整条序列一起增长。** GA 层仍需处理全局上下文，所以这个结论只适用于其中的 SWA 层。

> **Insight：长轨迹 RL 的探索预算，也取决于“每次尝试有多贵”。**
>
> 同一道题多试几次，才有机会得到不同做法，再用奖励区分哪些值得学。但每次尝试都要付出生成和训练长序列的成本。MiMo 的架构在两个方向上节省开销：MoE 减少每个 token 激活的参数，多数层使用局部注意力，减少长上下文的注意力与通信负担，同时保留全局层连接远处信息。
>
> **由此可以理解：降低单条轨迹成本，能为固定预算下的更多探索留出空间。** 这是架构与 RL 的联系。报告没有提供架构对照实验来量化这些设计究竟多换来了多少次探索，或单独贡献了多少 RL 性能提升。

具体配置如下，重点关注总参数与激活参数、局部与全局层数，以及窗口大小与上下文长度的区别：

| 配置 | MiMo-V2.6-Flash | MiMo-V2.6-Pro |
| --- | --- | --- |
| 总参数 / 激活参数 | 310B / 15B | 1.02T / 42B |
| 主干层数：Total / SWA / GA | 48 / 39 / 9 | 70 / 60 / 10 |
| Hidden size | 4096 | 6144 |
| SWA heads：Q / KV | 64 / 8 | 128 / 8 |
| GA heads：Q / KV | 64 / 4 | 128 / 8 |
| QK / V head dimension | 192 / 128 | 192 / 128 |
| Experts：总数 / 每 token 激活 | 256 / 8 | 384 / 8 |
| 主干 SWA window | 128 | 128 |
| 最终训练上下文支持 | 1M | 1M |

实现上，主体重复堆叠“若干连续 SWA 层 + 一层 GA”。首个 Transformer block 使用 GA + dense FFN，其余主干 block 使用 sparse MoE，没有 shared expert（所有 token 都固定调用的共享专家）。表中的主干层数不包含 MTP 模块。

### 1.2 多模态：让模型看懂环境，同时控制输入长度

来源：§2.1–2.3、Figure 2、Table 1。

**Agent 要根据环境的反馈决定下一步，而反馈可能是截图、视频或音频。** 例如，检查网页布局时，截图中的元素位置和文字一样重要；处理音频时，只保留转写文字则可能丢掉音乐或其他声音的信息。这些例子说明：要完成这类任务，模型需要把非文本内容也纳入判断。

MiMo 的做法是：先用视觉、音频编码器把原始输入变成主干模型能处理的表示，再与文本一起送入同一个 Transformer 主干。

```text
图像 / 视频 → 视觉编码器 → 映射到主干输入 ┐
音频 → 音频离散编码 → 合并与压缩 → 主干输入 ├→ 统一序列 → 主干模型
文本 → 文本 embedding                    ┘
```

这里有两个问题需要同时解决：**输入表示要保留任务所需的信息，也要避免图像和音频让序列过长。** 视觉侧主要通过混合注意力降低处理成本；音频侧则明确压缩进入主干的序列长度。

**视觉：既看局部细节，也连接整张图的信息。** 图像需要先排列成序列才能做注意力，但图像本身是二维的：只按行排列，上下相邻的内容在序列中可能相隔很远。MiMo-ViT 交替采用按行、按列的排列方式，让局部注意力在不同层沿两个方向传播信息，再定期用全局注意力汇总整张图。这样，多数层可以使用计算较省的局部注意力，同时保留跨区域的信息交流。

具体配置是 **681M 参数、28 层，其中 24 层局部注意力、4 层全局注意力**。局部层采用带 attention sink 的滑动窗口注意力（sink-augmented SWA）；相比固定、互不重叠的窗口，滑动窗口可通过多层传播连接窗口边界两侧的信息。作者将视觉编码器与一个可训练的小语言模型配对，用多模态理解任务的交叉熵目标训练，处理了超过 **4T image tokens**，没有额外使用对比学习目标。这意味着视觉表示是在帮助语言模型理解输入的训练过程中学出来的。

**音频：同一时刻的多个编码，先合成一个表示，再压缩时间长度。** 原文中的“25 Hz、20 个离散码、6.25 Hz”分别描述不同层次，可以按以下顺序理解：

1. Audio Tokenizer 把音频变成每秒 **25 帧**的表示。每帧用残差向量量化（Residual Vector Quantization，RVQ）得到 **20 个离散码**，它们共同描述同一帧。
2. 这 20 个码各自查 embedding 表，然后**相加成一个帧表示**，因此不会在主干序列中占据 20 个位置。
3. 每 **4 帧**组成一个小组，由 audio patch encoder 处理，再合成一个主干输入表示。进入主干的速率因此降为 **每秒 6.25 个位置**。

例如，按该速率估算，**60 秒音频对应约 375 个音频主干输入位置**，而不是把每帧的 20 个码全部展开后的 30,000 个位置。这个例子只计算音频表示，不包含文本或其他序列标记；它说明的是主干输入长度，不能据此断言整条音频处理链路的计算量也减少了 80 倍。Audio Tokenizer 本身在约 **2,000 万小时音频**上训练，覆盖语音、音乐及其他声音。

> **Insight：多模态 agent 需要同时解决“看到了什么”和“看这些信息要花多少成本”。**
>
> 视觉编码器决定图像中的哪些信息能够被主干利用，音频编码器则把高频、细粒度的声音表示压缩成更短的输入。对于不断接收环境反馈的长交互，输入表示越长，后续处理历史的负担就越重。因此，多模态编码方式也会影响 agent 能以什么成本持续观察环境。
>
> 这也说明，后续 RL 能利用的观察能力已经受到底座设计和预训练的影响。**RL 可以训练模型如何依据观察采取行动，但不能假定奖励会自动补回编码时丢失的信息。** 这是对机制的解读；报告没有通过单独消融量化上述视觉或音频设计带来的 RL 收益。

### 1.3 从预训练到蒸馏：每个阶段为下一步准备什么

来源：§3、§4 开头、§5.6、Figure 13。

**MiMo 的 RL 从一个已经具备知识、多模态理解和长上下文能力的模型开始。** 理解这条训练链路，关键是分清各阶段的分工：先建立基础能力，再适配 agent 任务和训练条件，随后通过任务反馈改进做法，最后利用多个教师合并、补充能力。

```text
预训练：学习文本知识，再加入图像、视频和音频理解
    ↓
Mid-training：学习 agent 交互，扩展上下文，适配后续训练的计算方式
    ↓
短期 SFT：监督微调，形成进入 RL 的起点
    ↓
Mixed RL：在多类任务和执行框架中尝试，根据反馈改进策略
    ↓
MOPD2：通过多个教师的监督，合并和拓展能力
```

**第一步，预训练：先建立语言底座，再接入多模态。** 第一阶段只训练文本主干；第二阶段接入预训练好的视觉、音频编码器，用多模态数据联合训练整个模型。这一阶段提供后续做任务需要的知识和输入理解能力。训练上下文从 32K 扩展到 256K，优化器使用 AdamW。

| 预训练数据量 | Flash | Pro |
| --- | --- | --- |
| 文本阶段 | 26T tokens | 27T tokens |
| 多模态阶段 | 22T tokens | 3T tokens |
| 总计 | 48T tokens | 30T tokens |

这里统计的是训练数据量：Flash 虽然参数更少，但预训练看到的 tokens 更多。不能只比较参数量，就认为两者经历了相同的底座训练。

**第二步，Mid-training：让通用底座适应即将开展的 agent RL。** 它处在预训练与后续 SFT、RL 之间，主要做三件事：

* **数据适配：让模型接触 agent 的交互过程。** 数据包含代码、通用、视觉、研究等任务的 agent 轨迹，也保留高质量文本、仓库级代码、图像、视频和音频。它让训练内容更贴近后续任务，同时继续训练通用与多模态能力。
* **长度适配：让模型处理更长的任务历史。** 先在 256K 上下文下投入大部分计算，最后扩展到 1M，为长交互做准备。
* **计算适配：提前适应大 batch 优化与低精度计算。** 作者在这个阶段切换部分参数的优化器，并引入量化感知训练，减少后续 RL 才改变计算方式带来的适配负担。

最后一点包含两个不同的选择，值得分开理解：

| 选择 | 为什么在这里做 | 具体做法 |
| --- | --- | --- |
| 切换到 Muon 的变体 Muown | 作者的初步实验发现，AdamW 在混合任务 RL 中随 batch 增大，优化效率的收益递减，因此提前为大 batch RL 做准备 | 隐藏层权重矩阵改用 Muown；embedding、输出层 LM head 和 MoE router 仍用 AdamW，router 到 RL 时再冻结 |
| 引入 MXFP4 量化感知训练（QAT） | 后续生成轨迹会使用低精度计算，需要让模型提前适应这种数值条件 | 在 mid-training 中就加入量化感知训练，而非等到 RL 采样时才引入低精度计算 |

**这里的 Muown 不是 Muon 的拼写错误，而是报告实际采用的 Muon 变体。** §3.2 原文明确写道：“a variant of Muon optimizer, Muown”。两者关系可以这样理解：

* **Muon** 利用权重矩阵的结构，对更新做正交化处理。
* **Muown** 在 Muon 的基础上增加显式的 **row-norm control（行范数控制）**，也就是控制权重矩阵每一行的大小。报告称，这样可以减轻谱范数漂移，并降低对 weight decay（权重衰减）设置的敏感性；其引用的方法论文为 [Muown: Row-Norm Control for Muon Optimization](https://arxiv.org/abs/2605.10797)。

因此，概括时可以说“从 AdamW 切换到 Muon 系列优化器”，但准确记录 MiMo 的配置时应写 **Muown**。理解训练链路时，重点是**优化器的适配提前发生在 mid-training**。作者报告这次切换没有出现 loss spike（损失突增），但这不等于已经证明所有 AdamW 模型都能无损切换。

**第三步，短期 SFT 后做 Mixed RL：让模型根据自己尝试的结果学习。** 报告只简要提到进入 RL 前有一段短期监督微调，没有在这里详细交代其数据规模和配方。随后开展混合任务 RL，覆盖代码、通用工具、视觉设计、上下文遵循和网络安全，并使用不同的 agent 执行框架。模型自己生成轨迹，再根据测试、评分标准或模型评审等反馈更新策略。这里的学习信号来自**尝试做得怎么样**，而不仅是已有示范怎么写。

**第四步，MOPD2：用教师监督合并能力，也补充难以直接做 RL 的任务。** Multi-Prefix Multi-Teacher On-Policy Distillation（多前缀、多教师在线策略蒸馏）接在 Mixed RL 之后。Figure 13 给出两类教师来源：通过 MixRL 训练的可验证任务领域教师，以及用合成示范进行 SFT 的开放任务教师。

蒸馏时，学生仍然自己生成内容，但学习信号改为教师对生成内容的逐 token 指导。学生既可以自主生成整条轨迹，也可以从教师轨迹或 SFT 示范的某个历史节点出发，只生成下一轮，再接受教师监督。这样，多个教师的能力可以汇入学生，难以设计可靠奖励的领域也能通过教师示范参与训练。具体路径见第 10 节；报告没有完整披露每个教师的训练配方与学生初始化细节。

> **Insight：这条链路说明，做好 RL 不只取决于奖励，还取决于进入 RL 前准备了什么。**
>
> 任务轨迹影响模型见过哪些交互方式，长上下文训练影响它能处理多长的历史，优化器和量化适配则影响后续大规模训练如何运行。Mid-training 把这些准备集中到 RL 之前，因此它是连接通用预训练与 agent RL 的重要环节。
>
> 评估结果时也要按阶段归因：**RL 过程中的前后对比反映这一阶段的变化，最终模型成绩则还包含后续蒸馏的作用。** 报告没有逐一隔离上述准备工作的贡献，不能从最终成绩反推出某一项设计单独带来了多少提升。

## 2. Scaling RL Compute：把算力变成有效的尝试、反馈和更新

**MiMo 扩大 RL 的关键，是让“生成尝试 → 评价尝试 → 更新模型”这三个环节一起扩展。** 生成更多轨迹提供探索机会，更细的评价决定哪些做法值得学，训练系统则要让长短不同的任务持续、稳定地参与更新。只看 GPU 数量或总 token 数，会漏掉这几个环节之间的制约。

### 2.1 一步训练包含什么：1,568 道题，每题尝试 16 次

来源：§4.1、§5.1。

MiMo 每步采样 **1,568 个 prompts**，对每个 prompt 生成 **16 条轨迹**。一条轨迹包含一次任务尝试中的多轮交互，不等于一句回答，也不等于一次工具调用。

```math
B_{\text{trajectory}} = B_{\text{prompt}} G = 1568 \times 16 = 25{,}088.
```

理解这组数字，要区分两个方向：

| 维度 | 这次运行的配置 | 对学习的作用 |
| --- | --- | --- |
| 一步覆盖多少题 | 1,568 个 prompts | 容纳来自不同任务、环境和执行框架的问题 |
| 同一道题尝试多少次 | 每题 16 条轨迹 | 在相同问题下比较不同尝试，形成组内相对学习信号 |

**更多题目和更多同题尝试，提供的是不同的信息。** 固定轨迹预算时，把预算分给更多题目，有利于增加问题覆盖；把预算分给同题更多尝试，则有机会观察同一问题的不同解法与成败差异。这是配置的取舍，报告没有给出组大小对照实验来证明 16 是最优值。

这些轨迹每步合计 **2.7B–3.7B training tokens**，平均每条序列约 **110K–150K tokens**。这是报告的训练序列统计，不能直接读成“模型每次新生成十几万 token”：上下文、工具返回与实际参与 loss 的模型输出需要区分。

> **Insight：采样量大，不等于有用的学习信号多。**
>
> 例如，同题 16 条尝试如果在二元测试下全部成功，单凭过测结果就无法判断应该更鼓励哪一种做法。反过来，如果能进一步判断实现质量和行为是否可靠，已生成的轨迹就可能提供更细的学习信号。
>
> 这解释了 MiMo 为什么同时投入 grader（评价器）计算：**探索产生差异，评价要把值得学习的差异识别出来。** 具体方法见 3.1；不能把所有采样 token 都视为等量的有效监督。

### 2.2 钱花在哪里：生成与评价合计超过一半

来源：§4.1、Figure 3。

MiMo 把 RL 计算分成三部分。**Rollout** 是让模型实际尝试任务；**grading** 是判断尝试的结果和质量；**training** 是用这些数据计算梯度、更新参数。

| RL 成本项目 | Pro | Flash | 这笔计算买到了什么 |
| --- | --- | --- | --- |
| Rollout：生成轨迹 | 43.8% | 44.9% | 模型自己探索得到的任务经历 |
| Grading：评价轨迹 | 12.7% | 14.2% | 区分成败与做法质量的学习信号 |
| Training：参数更新 | 43.5% | 40.9% | 将已有经历和反馈用于改进策略 |
| 本轮 RL 总成本 | 约 \$2.6M | 约 \$0.9M | 上述 RL 运行开销，不含整个模型研发与预训练成本 |

按报告比例推算，Pro 的生成与评价合计占 **56.5%**，Flash 为 **59.1%**；其中评价开销分别约为 **33 万美元、12.8 万美元**。这说明在该运行中，生产并评价学习材料的成本，已经超过参数更新本身。

> **Insight：RL 的算力分配，也是“如何生产训练数据”的决策。**
>
> 多花预算生成轨迹，可以增加尝试；多花预算评价轨迹，可以改善对尝试的区分；加速参数更新，则能降低把这些信息学进去的成本。三者需要一起考虑：如果评价始终无法区分有效做法与投机行为，仅增加采样并不能自动解决反馈质量的问题。
>
> MiMo 的数据说明 grader 已经是重要的预算项，但没有提供固定总预算下“更强评价器”和“更多采样”的直接对照。因此，**值得借鉴的是把反馈质量纳入算力规划，而不是照搬 12.7% 这个比例。**

### 2.3 为什么大 batch 要配合异步采样：少等待，也要付出续跑成本

来源：§4.1、§5.1、§6.2–6.3。

长任务的难点是结束时间不一致：有的很快完成，有的还在等待工具或继续探索。报告对 25 个数据源的分析显示，源间平均 rollout 耗时相差 **66 倍**，平均生成 token 数相差 **90 倍**。如果每轮都等最慢的任务结束，其余资源就可能长时间无法充分利用。

MiMo 使用 **asynchronous partial rollout（异步、可分段续跑的轨迹生成）**，staleness 配置为 **4**。其主要过程是：

1. 并行生成大量轨迹，持续收集满足训练要求的数据。
2. 收齐一批后，暂停尚未完成的轨迹，进行参数更新。
3. 下一轮恢复未完成任务，让长任务跨越多个采样阶段继续运行。

这样可以减少对长尾任务的等待，但存在代价：**模型参数更新后，续跑需要重新计算历史上下文的 KV cache**，即 re-prefill。这个过程不是新的任务探索，却仍然消耗计算。

**大 batch 为什么能缓解？原文给出了判断，但没有详细说明成立条件。** §4.1 写道“a large batch amortizes the re-prefill”（大 batch 摊薄 re-prefill 开销），并强调 batch 大小与 partial rollout 要联合选择。不能把这句话推成“只要扩大 batch，重算占比就一定下降”。

举一个反例：200 条轨迹中有 10 条中断，扩大到 1,000 条后有 50 条中断。如果平均重算历史长度、每条轨迹的有效生成量及其他执行条件都不变，那么有效计算与重算开销都扩大 5 倍，**重算成本占比不会下降**。

一种可能的机制是：在并发资源等条件固定时，更大的 batch 需要更久才能收齐，从而拉长两次参数更新之间的生成时间，让同一条长轨迹在完成前跨越更少的更新边界、少重建几次缓存。但**这是有条件的机制解释，并非报告验证的结论**。如果 batch 和生成并发同时扩大，更新间隔保持不变，就未必有这项收益。报告没有单独给出中断次数、重算历史量或 re-prefill 成本占比随 batch 变化的对照结果。

另一个已披露的优化是 **同一 policy version（策略版本）内复用上下文缓存**：后续交互轮次只计算新增后缀，不重复处理已有历史（§6.4，详见 8.3）。它节省的是参数未变时的重复计算，不能消除参数更新后的缓存重建。

因此，这里的确定性取舍是：**partial rollout 用部分历史重算换取更少的长尾等待；扩大 batch 能否降低重算占比，还要看并发、更新间隔和轨迹中断情况如何一起变化。** 大 batch 提供更多可并行工作的序列，同时增加路由记录、采样候选集、概率和多模态数据的存储与搬运压力。旧策略生成的数据如何用于当前策略更新，也需要相应处理，见第 3 节。

**异步系统还会改变“哪些任务先进入训练”。** 如果总是先用最快完成的轨迹填满 batch，慢任务可能长期不足。因此，保持任务配比需要专门调度，而不是把数据混在一起就结束了。

| 任务类别 | 报告给出的任务混合占比 |
| --- | --- |
| Agentic + competitive coding：agent 编程与竞赛代码 | 68% |
| General tool use：通用工具使用 | 12% |
| Aesthetic design：视觉设计 | 13% |
| Context following：上下文遵循 | 3% |
| Cybersecurity：网络安全 | 4% |

§5.1 没有进一步明确这五项比例的统计分母，因此不能直接标成 token 或 GPU 时间占比。§6.3 则说明，Sample Mixer 的调度目标以各数据源保留的样本组数量表达，并结合耗时、接受率与缺额安排采样。具体机制见第 8 节。

> **Insight：训练数据分布也由调度系统决定。**
>
> 举一个简化例子：两个数据源希望各贡献一半样本，但其中一个任务平均慢十倍。若只给它们相同的并发名额，再按完成顺序收数据，快任务就更容易占满 batch。要实现预定混合比例，必须给慢任务相应的资源或等待安排；若某个数据源过滤率高，还需要额外采样补足。
>
> 因此，**任务占比、采样工作量、算力占比是三件事。** 一个占比很小的慢任务源仍可能消耗大量资源。MiMo 的启发是：调度不只是提升吞吐的工程优化，也是落实训练配方的一部分。

### 2.4 扩大计算带来了什么：成绩上升，还要看解题成本

来源：Figure 3、Figure 9、Figure 12。

| 指标 | Pro | Flash |
| --- | --- | --- |
| DeepSWE average@3：RL 起点 → 终点 | 58.4 → 72.6 | 48.7 → 65.7 |
| 绝对提升（据上行相减） | 14.2 个百分点 | 17.0 个百分点 |
| Figure 12 的 30 步运行时间 | 123.1 h | 81.8 h |

这里的 **average@3 是三次尝试结果的平均，不是“三次里至少成功一次”的 pass@3**。Figure 3 显示，在这次 RL 运行中，两个模型的成绩随累计投入持续提升。运行时间包含故障与恢复，不能直接除以步数就当作纯训练计算耗时。

**成绩提高的同时，模型做题用的 token 也增加了。** Figure 9 展示了这一变化。更多 token 可能用于继续分析、调用工具、检查和修改结果。因此，读这些成绩时需要分清两个问题：

* **按训练后模型实际采用的做法，它能否完成更多任务？** 报告中的成绩上升支持这一点。
* **如果限制前后两个模型使用同样多的 token，训练后的模型还能提高这么多吗？** 这里的实验没有回答这个问题。

用一个假设例子理解：模型训练前每题平均用 1 万 token，能做对 60% 的题；训练后平均用 2 万 token，能做对 70%。这说明新模型在这样的资源使用下，完成任务的成功率更高。但如果产品要求每题最多用 1 万 token，新模型能否仍达到 70%，需要重新测试。**这个例子仅用于解释，不是 MiMo 的实验数字。**

> **Insight：既要看“多做对了多少”，也要看“为此多做了多少工作”。**
>
> RL 可能让模型学会更有效的解题方法，也可能让它学会在结束前多检查、多尝试。后者同样有价值，但通常伴随更多 token 消耗；两种变化可以同时发生，仅凭成功率与 token 一起上涨，无法拆分各自贡献。
>
> 判断实际收益，可以做两种比较：**给相同的解题预算，看谁做对更多；要求达到相同的成功率，看谁花费更少。** MiMo 这里展示了训练后成功率提高、token 使用也增长，尚未给出上述预算匹配结果。

还要把这笔“每次做题的开销”与前面的 RL 训练费用分开：**训练费用是获得这个模型的投入，解题费用是部署后每次使用它的开销。** token 数只是解题成本的一个指标，实际费用和耗时还取决于模型大小、工具调用及执行环境。

## 3. RL 目标：GRPO 基础上的几项关键选择

来源：§4.1 Eq. (1)、§5.1；细粒度评价见原文 §4.3。

MiMo 使用 **Group Relative Policy Optimization（组相对策略优化，GRPO）**。优势与重要性采样都是已有机制；本节重点是如何引入质量反馈、按题分配权重，以及分别限制正负更新。

| 设计 | 作用与定位 |
| --- | --- |
| 细粒度评价与优势分配 | 用 LLM judge 区分成功方案的质量，是比基础 GRPO 更值得关注的部分，详见 3.1 |
| Prompt-mean（按题平均） | 聚合方式的小改动，改变长短题目的训练权重 |
| 逐 token 重要性采样 | 已有方法；跨版本 rollout 必须保留真实生成概率 |
| 正负优势分别设置 mask | 更有 MiMo 配方特色：四个独立边界随熵调整，但未披露完整控制器与独立消融 |

### 3.1 质量反馈：测试判断能不能过，LLM judge 辅助判断过得好不好

**MiMo 用 judge 辅助评价，再通过奖励或优势决定模型重点学谁。** 三项改动的位置不同：

| 机制 | 具体怎么做 | 改动位置 |
| --- | --- | --- |
| Groupwise Reward Synthesis（组内奖励合成，GRS） | 离线比较同题尝试、提炼评分标准；在线逐条评分，奖励为“测试分 × 实现质量分 × 行为质量分” | Reward：通过测试的方案也能得不同分 |
| Groupwise Advantage Redistribution（组内优势重分配，GAR） | 在线比较同题成功方案，把更多正优势分给质量较好的方案 | Advantage：改变成功轨迹的学习权重 |
| 局部行为惩罚 | 用规则识别无效工具名、畸形参数等片段；正优势轨迹中这些片段的优势置零，负优势轨迹中加重惩罚，并对正常部分重平衡 | Token advantage：不让错误调用随最终成功一起被强化 |

例如，GAR 可将两个成功方案原本各 +0.5 的优势重新分成 +0.8、+0.2，让更好的方案获得更多鼓励。这是未加缩放上限的示意；实际还有限幅与全组重新中心化，保证最终组均值为零，但不保证原正优势总和不变。

**GRS 与 GAR 用于不同代码任务子集，不是固定串行步骤。** 它们主要区分哪条轨迹值得学，局部惩罚则处理规则能识别的错误片段；并未精确识别每一步对成功的因果贡献，judge 也可能误判。局部行为惩罚的公式与例子见第 6 节；GRS/GAR 的完整定义见原文 §4.3。

### 3.2 Prompt-mean：让长题不再仅凭 token 多就占更大权重

MiMo **先对同题轨迹组的 token 项平均，再在题目之间平均**。例如，两道题的轨迹组分别有 1 万、10 万 token：全 batch 按 token 平均时，名义权重约为 1:10；按题平均后，外层权重为 1:1。

```math
\mathcal{L}(\theta)
= -\mathbb{E}_{q\sim\bigcup_d\mathcal D_d,\;\{o_i\}_{i=1}^{G}\sim\mu_{\theta_{\mathrm{old}}}(\cdot\mid q)}
\left[
\frac{1}{\sum_{i=1}^{G}\lvert o_i\rvert}
\sum_{i=1}^{G}\sum_{t=1}^{\lvert o_i\rvert}
r_{i,t}M_{i,t}A_i
\log\pi_\theta(o_{i,t}\mid q,o_{i,\lt t})
\right].
```

公式内层将各 token 的对数概率乘以优势、重要性权重和 mask，再除以同题轨迹组总长度；外层对题目与采样取平均。

| 符号 | 含义 |
| --- | --- |
| $`q`$、$`G`$ | 题目及每题轨迹数，本次 $`G=16`$ |
| $`o_{i,t}`$、$`o_{i,\lt t}`$ | 第 $`i`$ 条轨迹的当前 token，以及之前的历史 |
| $`\pi_\theta`$、$`\mu_{\theta_{\mathrm{old}}}`$ | 当前训练策略，以及实际生成数据的策略 |
| $`A_i`$ | 轨迹优势；加入局部行为调整后，需要使用相应的逐 token 优势 |
| $`r_{i,t}`$ | 生成时与训练时概率差异对应的重要性采样权重 |
| $`M_{i,t}`$ | token mask；还需结合模型输出的训练范围及行为规则理解 |

> **Insight：任务配比相同，loss 的平均方式不同，实际学习侧重点仍会不同。** 按题平均消除了长题在外层聚合中的长度优势，但不保证各题梯度大小相同，同题内部也不是每条轨迹等权。报告称它有助于抑制过快的长度增长；它改变的是题目权重，并非直接给长答案扣分。

### 3.3 逐 token IS：分母必须是真正生成时的概率

Partial rollout 的不同片段可能由不同策略版本生成。MiMo 使用逐 token 的 importance sampling（重要性采样，IS）权重：

```math
r_{i,t}
=\operatorname{sg}\left[
\frac{\pi_\theta(o_{i,t}\mid q,o_{i,\lt t})}
{\mu_{\theta_{\mathrm{old}}}(o_{i,t}\mid q,o_{i,\lt t})}
\right].
```

分子是当前模型的概率，分母是该 token **生成当时保存的概率**；报告明确说不为 partial rollout 重新计算生成概率。不能用某个统一旧版本事后补算，否则会改变权重的含义。$`\operatorname{sg}`$ 表示停止梯度，ratio 只作权重，梯度经总目标的 log-probability 项传播。

### 3.4 正负更新分开控制：越界 token 直接屏蔽

MiMo 为正、负优势分别设置概率比上下界，共四个边界：

```math
M_{i,t}^{\mathrm{clip}}=
\mathbf{1}\left[
(A_i\geq0\land\epsilon_+^{l}\leq r_{i,t}\leq\epsilon_+^{h})
\lor
(A_i\lt0\land\epsilon_-^{l}\leq r_{i,t}\leq\epsilon_-^{h})
\right].
```

两组区间初始均为 **[0.2, 5.0]**。越界 token 的 clip mask 为 0，不贡献这一策略梯度项；例如 ratio 为 6 时是屏蔽，不是截成 5 后继续更新。因此不能直接替换成标准 PPO 的 `min(unclipped, clipped)` 目标。

训练中按策略熵调整，并监控两个方向的 token 屏蔽比例：

| 情况 | 正优势区间 | 负优势区间 |
| --- | --- | --- |
| 熵过低 | 放宽 | 收窄 |
| 熵过高 | 收窄 | 放宽 |

**值得关注的是鼓励与抑制可以分开调节。** 但上述熵控制方向是报告的运行策略，其效果依赖实际概率和梯度分布，并非普遍定理；完整阈值与控制器未披露。也不应自行补上报告目标中没有写出的参考模型 KL 惩罚或默认优势标准差归一化。

### 3.5 优化器与初始化配置

Muown 是加入行范数控制的 Muon 变体，见 1.3。具体配置保留如下，供查阅：

| 项目 | 报告配置 |
| --- | --- |
| 优化器 | Muown |
| Learning rate | $`3\times10^{-6}`$ |
| Weight decay / LR warmup | 均不使用 |
| Gradient clipping | 1.0 |
| Muon momentum | 0.95，启用 Nesterov |
| Newton–Schulz iterations | 10 |
| 额外 update scaling | 0.5 |
| Adam 部分 | $`\beta_1=\beta_2=0.95`$，$`\epsilon=10^{-8}`$ |
| RL 初始化 | 继承 SFT 的 FP32 master weights 与 Muown row state |
| MoE router | 冻结 |

**复现时要保留训练状态。** 为稳定 MXFP4 训练，RL 继承 SFT 的高精度主权重与 Muown 行状态；只加载量化推理权重，不是相同初始化。

## 4. 环境建设：让奖励反映任务是否真正完成

来源：§4.2.1–4.2.5、Figure 4–5；多框架训练另见 §6.2、Figure 10。

**训练 agent，需要同时准备题目、执行环境和评分规则。** MiMo 在这一部分重点解决两个问题：让任务能稳定地重复执行，让评分尽量符合真实需求。不同领域的任务使用不同检查方式，LLM judge 只是其中一部分。

### 4.1 代码任务：检查测试是否准确、稳定

代码任务来自 GitHub issues/PRs、员工开发需求、详细规格、既有代码功能和长程工程任务，另有公开与授权数据。需求不完整时，可以从参考补丁和仓库上下文重建题面，但要去掉泄露解法的细节。

**测试本身也需要检查：既不能放过错误实现，也不能拒绝满足需求的其他实现。** 例如，题目只要求函数支持空输入，测试却强制调用参考补丁中的某个内部函数，就可能排除另一种正确实现。这是解释性例子，不是论文案例。

| 检查 | MiMo 的做法 | 作用 |
| --- | --- | --- |
| 需求与测试对齐 | 检查是否遗漏需求，或增加了题面没有要求的限制 | 让测试检查功能，而不是要求实现照搬参考补丁 |
| 实际解法审计 | 每题尝试 **4 次**，审计 agent 联合查看需求、测试、参考补丁、提交与执行记录 | 找出“过测但不符合需求”或“符合需求却未过测”的任务，提交复查 |
| 重复执行 | 有参考补丁时，检查补丁前后的测试状态，并要求 **8 次重跑**结果稳定 | 排除偶发失败与环境噪声 |

最后一项包括两类测试：**F2P（fail-to-pass）** 在修复前失败、修复后通过；**P2P（pass-to-pass）** 在修复前后都通过，检查已有功能没有被破坏。

> **Insight：这里的审计 agent 是在帮助筛选训练题，而不直接替代测试。** 它与测试结论不一致，说明任务值得复查，不代表审计判断一定正确。实际 rollout 的价值是提供具体反例，暴露仅检查题面和测试代码时容易遗漏的问题。

### 4.2 通用工作流：固定任务起点，检查实际结果

办公任务会修改文件、数据库和软件状态。**同一道题的多次尝试，需要从相同状态开始。** 例如，第一次尝试更新了库存，第二次不能接着使用更新后的数据，否则两次得分就难以比较。

MiMo 为每条轨迹提供独立、可恢复初态的 sandbox。依赖在线服务的软件使用 **本地 mock（模拟实现）**，复现支持的操作、状态变化、输出格式与错误响应；可离线工作的工具直接集成。生成环境时，还要检查文件与数据库之间的名称、数值、时间线和引用是否一致。

评分将任务拆成可单独判断对错的条目，再选择合适的检查方式：

| 内容 | 检查方式 |
| --- | --- |
| 数据库值、文件格式等确定性要求 | 代码检查 |
| 开放式报告、分析等内容要求 | LLM judge；训练时使用自部署的 MiMo-V2.6-SFT |
| 是否误改无关文件或数据库 | 增加负面检查 |

这些评分条目也需要修订：重复调用同一 judge、换不同 judge，发现含糊标准；再结合不同能力模型的轨迹与对抗方案，检查标准是否过严或过松。

> **Insight：评分稳定，不代表评分正确。** 以“更新库存并生成报告”为例，judge 可能稳定地接受一份声称更新成功的报告，却没有检查数据库是否真的改变。这个假设例子说明，评价必须结合执行结果，不能只看最终回复。可重置环境减少了网络与服务波动，但本地模拟仍可能遗漏真实软件的行为。

### 4.3 视觉与安全：根据任务选择评分方式

**能直接检查的结果，优先用规则；难以写成规则的质量差异，再用模型评价。** MiMo 在这几类任务中采用了不同分工：

| 任务 | 评价方式 | 原因 |
| --- | --- | --- |
| 开放式视觉设计 | 先逐件检查运行、指令遵循、布局和基础审美，再比较同题渲染成品 | 没有唯一参考图，需要区分多个合理方案的质量 |
| 按图复刻 | 以像素相似度等规则指标为主，LLM 补充整体视觉判断 | 有明确目标，可以直接衡量还原程度 |
| 指定漏洞复现 | 检查漏洞类型与崩溃位置是否同时匹配 | 触发其他崩溃不能算完成目标任务 |

安全任务的题面与验证规则来自同一份 **sanitizer report（运行时错误报告）**。验证时匹配漏洞类型，以及最上层项目代码栈帧对应的位置；环境提供源码与编译好的测试入口程序，允许模型根据运行反馈分析。

**这项设计的重点是让题目描述与评分检查同一个目标。** 类型与位置匹配是实用判据，并非完整的漏洞等价证明。报告使用修正后的 CyberGym 环境，与其他成绩比较时需要核对版本。

### 4.4 多执行框架：降低对固定工具接口的依赖

**Harness 是模型执行任务时使用的框架**，包括系统提示、工具定义、上下文管理和 agent 循环。任务内容可以不变，但框架变化会改变模型调用工具、读取历史和接收结果的方式。

MiMo 把这些组件拆成可重组的 **mini-harness**，用不同组合训练。相比直接混用完整生产框架，这样更容易单独调整交互方式；生产框架中的额外要求也未必都能被任务奖励覆盖。

**同一题的一组轨迹使用相同配置，不同组可以使用不同配置。** 前者保持组内比较条件一致，后者扩大模型见过的交互方式。

训练期间，在未见过的 Codex、Claude Code、mini-swe-agent 框架上，DeepSWE 平均 Pass@1 约从 **50% 提升到 66%**。这支持能力能够迁移，但缺少计算匹配的单框架训练对照，不能把提升全部归因于框架多样性。

> **Insight：扩充题目与更换执行框架，训练的是不同方面。** 前者增加任务覆盖，后者减少策略对特定工具和上下文管理方式的依赖。跨框架评测因此能检查常规任务评测没有覆盖的适应能力。

## 5. Reward Hacking：防止模型绕过任务获得奖励

来源：§4.2.6、Table 2、Figure 6。

**Reward hacking 指模型利用环境或评分漏洞获得高分，却没有按任务要求完成工作。** 报告重点讨论代码修复中的答案泄露：任务要求基于指定历史版本修复问题，模型却从新版软件或上游仓库取得已经发布的补丁，再移植回来通过测试。

Table 2 记录了实际轨迹中的几类行为：安装新版包并读取源码、下载或克隆上游代码、搜索 issue/PR 中的现成修复。**查询上游在实际开发中可以合理，但在这些训练任务中绕过了要求学习的修复过程。** 是否构成 hacking，取决于任务允许的信息范围。

### 5.1 同时处理模型行为、环境泄露与评分结果

只在提示词中禁止获取答案不足以解决问题。MiMo 在四个环节处理：

| 环节 | 具体做法 | 作用 |
| --- | --- | --- |
| Mid-training | 根据早期 hacking 案例生成纠错数据，保留原错误并展示修正后的行动 | 训练模型遵循任务边界 |
| 环境准备 | 清除残留补丁、日志、验证输出及可能泄露答案的项目二进制、字节码和缓存；移除 base commit 之后的历史与引用；隔离网络 | 减少从本地或外部取得现成答案的途径，同时保留离线构建所需依赖 |
| 训练前对抗检查 | 专门的 hack agent 搜索泄露和漏洞，发现后修补环境，再重复测试 | 检查清理规则未覆盖的路径 |
| 训练中审计 | 持续检查新轨迹并修订环境；在线 groupwise grader 对确认 hacking 的轨迹将有效奖励置零，再重算组统计与优势 | 防止已经发现的违规成功继续获得强化 |

环境泄露不一定来自网络。例如，构建环境时曾应用参考补丁，之后即使还原了源码，构建产物或缓存仍可能保留解法信息。因此，清理需要覆盖仓库外缓存，不能只检查当前 Git 工作区。

### 5.2 如何理解“低于 2%”

最终运行中，Flash 和 Pro **被确认存在 hacking 的轨迹占比均保持在 2% 以下**。这是检测到并确认的比例，不代表所有未发现的漏洞都已消除。同样，hack agent 未找到有效路径，只能说明这一轮测试没有发现问题。

> **Insight：奖励漏洞会随策略能力变化，需要在训练中持续检查。** 训练前的对抗测试无法覆盖模型后来发现的全部捷径。环境修补减少漏洞，奖励归零阻止已确认的违规轨迹继续被鼓励，二者解决的是不同环节的问题。

## 6. 行为约束：控制冗长，避免强化错误调用

来源：§4.3.3、Eq. (4)–(5)。

**最终成功，不代表整条执行过程都值得强化。** MiMo 增加两项约束：在已有足够成功样本时，降低过长解法的奖励；对格式和工具调用错误，直接调整对应 token 的优势。前者控制轨迹长度，后者处理局部错误，均不同于 LLM judge 对方案质量的比较。

### 6.1 长度惩罚：用同题成功解作参照，而非统一限制长度

固定长度标准容易误伤复杂任务。MiMo 的做法是**先判断这道题是否已有足够高的通过率，再比较成功解之间的长度**：

1. **通过率超过阈值才启用。** 低通过率组保持原奖励，给困难任务保留探索空间。
2. **只用同题成功轨迹确定参考长度。** 取这些轨迹生成 token 数的指定分位数，避免用快速失败的轨迹作为效率标准。
3. **只对超出容忍范围的成功轨迹扣分。** 越长扣得越多，达到上限后不再增加；再由调整后的奖励计算优势。

设成功集合为 $`\mathcal P_q`$、每题轨迹数为 $`G`$。当 $`\lvert\mathcal P_q\rvert/G\gt a_{\min}`$ 时，参考长度为：

```math
\ell_q^\star=\operatorname{Quantile}_{B/100}
\{\ell_j:j\in\mathcal P_q\}.
```

长度惩罚为：

```math
\widetilde R_i=R_i-\mathbf{1}[i\in\mathcal P_q]X
\left[
\operatorname{clip}\left(
\frac{\ell_i/\ell_q^\star-1-\delta}{s-\delta},0,1
\right)
\right]^\gamma.
```

$`\ell_i`$ 是生成 token 数，$`B`$ 决定参考分位数；$`X`$ 是最大扣分，$`\delta`$ 是允许超出的比例，$`s`$ 决定何时扣满，$`\gamma`$ 控制扣分曲线。其中 $`s\gt\delta\geq0`$、$`X\geq0`$、$`\gamma\geq1`$。本文将原文通过率阈值 $`A`$ 改记为 $`a_{\min}`$，避免与优势混淆。

**假设例子**：参考长度为 10,000 tokens，容忍比例为 20%，则超过 12,000 才开始扣分；若 $`s=1`$，到 20,000 时扣满 $`X`$。这些数值仅用于说明，报告没有披露完整超参数配置。

> **Insight：这里优化的是“成功之后的效率”，而不是一律偏好短输出。** 通过率门槛决定何时开始约束，同题成功解决定约束尺度。但长度仍是成本指标，不等于质量判断：更长的轨迹可能包含必要验证，因此这项惩罚需要容忍区间，也不能替代质量评价。

### 6.2 局部惩罚：按优势正负处理错误片段

假设模型先发出一次无效工具调用，纠正后完成任务。如果把正优势用于整条轨迹，错误调用也会得到鼓励。MiMo 用规则标记格式破损、无效工具名、畸形参数等 token，再区别处理：

| 轨迹的优势 | 被标记的错误 token | 未标记的 token |
| --- | --- | --- |
| 正优势 | 优势设为 0，取消鼓励 | 适当增加正权重 |
| 负优势 | 放大负权重，加重惩罚 | 减轻负权重 |
| 零优势 | 保持为 0 | 保持为 0 |

**分支依据是优势正负，不是直接依据测试成败。** 奖励经过质量或长度调整后，成功轨迹也不一定具有正优势；另外，未标记只代表规则没有检测到错误，不代表行为已被证明正确。

令 $`h_{i,t}=1`$ 表示命中规则，否则为 0。调整后的逐 token 优势替换总目标中的轨迹优势：

```math
\widetilde A_{i,t}=\begin{cases}
\alpha(1-h_{i,t})A_i,&A_i\gt0,\\
[\beta(1-h_{i,t})+\kappa h_{i,t}]A_i,&A_i\lt0,\\
0,&A_i=0,
\end{cases}
\qquad \kappa\gt1.
```

$`\kappa\gt1`$ 决定错误片段的负权重放大多少；$`\alpha`$ 补偿未标记的正优势 token，$`\beta`$ 减轻未标记的负优势 token。**补偿是为了避免局部纠错顺便大幅改变整体正负权重。**

以两组假设 token 为例，且均未触发缩放限制：

| 原始权重 | 10 个错误 token 调整后 | 90 个未标记 token 调整后 | 总和 |
| --- | --- | --- | --- |
| 100 个 token，各 +1 | 全部为 0 | 各为 100/90 | 仍为 +100 |
| 100 个 token，各 −1，取两倍惩罚 | 各为 −2，合计 −20 | 各为 −80/90，合计 −80 | 仍为 −100 |

计算补偿系数时，统计范围是**整个 training batch 中参与 loss 的 token**，不是每条轨迹或每道题各自补偿。以 $`H_+,H_-`$ 表示正、负优势中命中规则的 token 集合，$`C_+,C_-`$ 表示未命中的集合：

```math
\alpha=\min\left(\alpha_{\max},
1+\frac{\sum_{(i,t)\in H_+}A_i}{\sum_{(i,t)\in C_+}A_i}\right),
\qquad
\beta=\max\left(\beta_{\min},
1-\frac{(\kappa-1)\sum_{(i,t)\in H_-}\lvert A_i\rvert}
{\sum_{(i,t)\in C_-}\lvert A_i\rvert}\right).
```

$`\alpha_{\max}\geq1`$ 限制正向放大，$`0\lt\beta_{\min}\leq1`$ 限制负权重减轻的程度。分母为零时，相应系数设为 1。**只有未触发限制、且分母非零时，正负两侧的优势总量分别守恒**；这不保证最终梯度或策略熵不变。

> **Insight：这是一种有限的局部纠错，并未精确判断每一步对成功的贡献。** 规则能识别明确的格式与调用错误，却无法覆盖所有无效推理。正优势轨迹中的错误被取消鼓励，而非直接改成负优势；负优势轨迹中才加重惩罚。读公式时，这个区别比“加入行为惩罚”的概括更重要。

### 6.3 与前面机制的区别

| 机制 | 改动位置 | 主要作用 |
| --- | --- | --- |
| Prompt-mean | 题目之间的 loss 权重 | 避免长题仅凭 token 多就占更大份额 |
| GAR | 成功轨迹之间的优势 | 让质量更好的方案获得更多鼓励 |
| 同题相对长度惩罚 | 成功轨迹的奖励 | 在通过率足够高时降低过长解法的奖励 |
| 局部行为惩罚 | token 优势 | 避免最终结果掩盖明确的过程错误 |

**这四项作用于不同层次，不能统称为“惩罚长答案”。** 报告未提供完整组合消融，也未完整披露它们与数据过滤的执行顺序，因此不能将各机制拼成未经验证的实现流程，或分别归因最终收益。

## 7. 稳定性：控制专家负载，对齐生成与训练

这一节解决两类不同的问题：**训练更新会不会让专家负载失衡，以及训练计算是否对应轨迹实际生成时的执行方式。** 前者通过冻结 router 处理，后者需要对齐权重、路由和采样概率。

### 7.1 冻结 router：限制不必要的路由变化

来源：§5.4、Figure 11。

MoE 的 router 决定每个 token 使用哪些专家。少数专家接收过多 token，会造成负载集中：即使其他专家较空闲，繁忙专家仍可能增加执行与显存压力。因此，**模型分数上升不代表计算资源的使用仍然健康**。

作者比较两个仅在 router 是否冻结上不同的 Pro RL runs，跟踪第 9 个 decoder layer 的 384 个专家：

| 指标 | Router 可训练：前 20 步 | Router 冻结 |
| --- | --- | --- |
| 负载变异系数 CV：越大越不均衡 | 0.78 → 2.0 | 约 0.7 |
| 最繁忙专家负载 / 平均负载 | 6 倍 → 16 倍 | 约 5.5 倍 |
| 负载低于均值 10% 的专家占比 | 0.5% → 22% | 约 1% |

**关键证据是一次单独恢复 router 的实验。** 作者保留第 20 步的其他参数，只把 router 恢复到 RL 开始前的值：负载平衡恢复到接近初始，评测性能基本不变。冻结 router 的训练中，性能也能正常提升。

> **Insight：在这次实验中，router 的更新使负载变差，但恢复旧 router 没有让评测成绩下降。** 作者只恢复 router，保留专家等其他参数，因此负载恢复说明：问题主要来自 token 被重新分配到哪些专家，而非专家权重已经损坏。
>
> 这为冻结 router 提供了直接依据：**保留原来的路由参数，让其他权重继续学习，可以维持负载稳定，同时继续提升能力。** 结论限于报告的实验设置；冻结维持的是相对稳定的负载，并不保证专家使用完全均匀。

冻结的是 router 参数，**不是每个 token 的专家选择**。其他层仍在更新，送入 router 的表示会变；不同计算引擎的数值误差也可能改变选择。这就是下面的路由重放仍有必要的原因。

### 7.2 三层对齐：相同权重不保证相同计算路径

来源：§6.4。生成使用 SGLang，训练使用 Megatron-LM，rollout 的专家权重采用 MXFP4。

| 不一致发生在哪里 | MiMo 的处理 | 对齐什么 |
| --- | --- | --- |
| 低精度表示：生成侧使用量化后的专家权重 | 每次更新后进行 QDQ（quantize–dequantize，量化再反量化），遵循生成侧 MXFP4 计算内核的数值约束 | 两个引擎使用的专家权重数值 |
| 专家选择：即使权重相同，数值误差也可能改变 top-k 结果 | R3（Rollout Routing Replay，生成路由重放）：保存生成时选中的专家编号，训练时重放 | 实际经过的专家路径 |
| 采样概率：top-k/top-p 只在候选集合内重新归一化 | 保存生成时的候选集合，训练时在同一集合内计算归一化概率 | 概率计算的范围 |

**这三项逐层补充，不能互相替代。** QDQ 对齐权重后，离散的专家选择仍可能变化；重放专家路径后，采样概率的归一化方式仍需单独对齐。

### 7.3 保存采样候选集：避免把计算口径差异当成策略变化

假设生成时某 token 的全词表概率是 0.2，top-p 保留的候选集总概率是 0.8，则实际采样概率是 **0.2 / 0.8 = 0.25**。即使策略没有变化，训练侧若直接用全词表概率 0.2 与生成概率 0.25 相除，也会得到 0.8，而不是 1。

这个假设例子说明：**概率比的变化可能来自归一化口径，而不来自模型更新。** 若生成时的候选集合为 $`S_t`$，训练侧应在这个集合内计算：

```math
\pi_\theta^{S_t}(y\mid h_t)=
\frac{\pi_\theta(y\mid h_t)}{\sum_{v\in S_t}\pi_\theta(v\mid h_t)},
\qquad y\in S_t.
```

其中 $`h_t`$ 是当前历史，$`y`$ 是采样 token。需要保存的是**生成当时的集合**，不是用更新后的模型重新选择一套 top-p 候选；只保存被采样的 token，也无法计算整个集合的概率和。

实现上，候选集在 GPU→CPU 传输时用固定大小的全词表位图，避免变长传输引入同步或截断；后续改用稀疏存储。报告中典型 top-p=0.97 时，平均候选数小于 5，但这是该运行中的统计，不是通用性质。

> **Insight：重要性采样之前，先保证分子、分母比较的是同一种概率。** Router 冻结控制参数漂移，路由和候选集重放减少执行方式的差异，IS 则处理生成策略与当前策略的概率变化。前两类措施不能消除异步数据的陈旧性，IS 也不能替代对实际生成过程的正确记录。

## 8. 训练系统：提高吞吐，同时保持训练数据分布

来源：§6.1–6.4、Figures 14–16。

**长轨迹 RL 不仅要生成得快，还要保证各类任务按预定比例进入训练。** MiMo 的系统设计主要处理数据搬运、异步调度和多轮生成中的重复开销。

### 8.1 执行与数据：避免逐轨迹创建进程、集中搬运整批数据

每步约 2.5 万条轨迹，每条还携带生成概率、专家路由、采样候选集和多模态输入。MiMo 用常驻进程承载多个并发任务；调度节点只处理奖励、长度和数据索引，大数据保存在分布式存储，训练设备按需读取。

一条轨迹可能包含主对话、子 agent 分支和压缩后的上下文，因此系统分别记录这些上下文，按前缀关系复用历史。多模态训练中，先分配图像编码工作，再将表示送到对应 token 所在的设备。

**关键点：不同资源需要分别平衡。** 文本 token 分片均匀，不代表图像编码量均匀；进程池分配比例，也不等于任务在训练 batch 中的目标比例。

### 8.2 Sample Mixer：训练配比需要调度来实现

25 个数据源的平均生成 token 数相差 **90 倍**，平均活跃 rollout 耗时相差 **66 倍**。部分生成结果还会被过滤，因此不能简单按完成顺序填满 batch。

**假设例子**：A、B 每步都需保留 100 组。A 接受率为 0.5、耗时 10 分钟，B 接受率为 1、耗时 1 分钟。预计分别要生成 200、100 组；维持相同目标收集速率时，并发需求比约为 **20:1**。相同任务配比，并不意味着相同资源投入。这里的接受率是组通过训练过滤的比例，不是测试通过率。

| 机制 | 核心作用 |
| --- | --- |
| 自适应并发预算 | 根据目标数量、接受率与耗时，为慢源和低接受率源分配更多在途任务 |
| 自适应调度 | 同时考虑当前 batch 的缺额和长期目标，避免某源收齐后完全停发、下一批断供 |
| 预测式分发 | 同时估计 KV 容量和实际推理并发，选择有余量的设备 |
| 启动/恢复回放 | 仅在首个收集步，对选定慢源复用符合过滤与策略版本条件的完整组，补足缺额 |

> **Insight：调度会改变模型实际学到的数据。** 快任务容易先进入 batch；即使各源数量达标，慢源内部也可能偏向较短的轨迹。保持任务比例之外，还要关注长度与策略版本分布。只检查 GPU 利用率，无法发现这些偏差。

Figure 16 的模拟支持该调度改善收集平衡，但未包含参数训练、学习信号计算延迟、过期数据淘汰和回放，不能直接当作全系统加速率。调度公式见原文 Eq. (6)–(7)。

### 8.3 Context Cache：等待工具时，不必持续占用显存

同一策略版本内，后续轮次复用历史 KV，只处理新增内容，历史图像也无需重复发送。等待工具时，轨迹状态移到主机内存；继续生成时再恢复到显存。策略更新或缓存未命中后仍需重建，不能消除跨版本 re-prefill。

> **Insight：活跃轨迹数不等于 GPU 请求数。** Agent 可能仍在执行任务，却正在等待工具。分层缓存把显存更多留给当前生成的请求；调度也应同时考虑任务状态占用和实际推理负载。

### 8.4 推测解码：接受长度不是最终优化目标

DFlash 用较小模型提出候选 token，再由主干并行验证。它先在 SFT 策略上训练，再用匹配 RL 任务配比的早期轨迹微调；实际 RL 默认使用 **block-6**。

| 比较 | 报告结果 |
| --- | --- |
| 默认 block-6 相比原 MTP 配置 | 平均接受长度高 31.3% |
| 混合 RL 中 block-6 相比 block-8 | 全局平均吞吐高约 6%，平均接受长度变化很小 |
| 所测长上下文负载下，RL 适配的 FP8 DFlash 相比基线 | 每节点吞吐高约 10.3% |

**Insight：候选更多或接受更长，不保证整体更快。** 较长候选块也增加主干验证工作。block-6 与 block-8 的比较表明，应按端到端吞吐选配置，而非只优化接受指标。三项结果的基线不同，不能相加。

## 9. 失败分析：平均值正常，局部峰值仍可能导致中断

来源：§5.5、Figure 12。

报告公开了 30 步训练中的故障与恢复记录。除了 GPU 显存双比特错误、Kubernetes 故障和 grader 网络不可达，更值得关注的是：**资源估计与真实执行负载之间的偏差如何导致内存耗尽（OOM）。**

| 故障位置 | 报告观察 | 核心问题 |
| --- | --- | --- |
| 轨迹生成 | 启动后短轨迹先完成，长度估计偏低，随后 GPU 与主机 KV 缓存池耗尽 | 已完成样本不能代表仍在运行的长任务 |
| 重启后的资源估计 | 同一代码数据集下，某 harness 的轨迹不到其他 harness 的一半长，再次影响长度估计 | 数据源相同，不代表执行成本相同 |
| 参数训练 | 完整 batch 相对均衡，但某个 micro-batch 中，一层的专家并行 rank 接收了超过均值 **30 倍**的 token | 总体均衡掩盖局部峰值；作者通过调整并行配置降低激活内存压力 |
| 训练数据打包 | Flash 后期序列变长，单节点数据超过主机内存，即使打包已分布到多节点仍发生 OOM | 分布式处理没有消除单节点容量限制 |

这些故障带来三个直接启发：

* **启动和恢复阶段需要更保守的估计。** 最先完成的任务天然偏短，直接用它们预测所有在途任务，会系统性低估需求。按 harness 等执行条件细分统计、为未完成长任务预留余量，是由这些故障得到的设计启示，而非报告已验证的完整修复方案。
* **容量要按实际执行单元检查，不能只看全局平均。** 全 batch、单个 micro-batch、单层专家和单个设备的负载是不同尺度。第 7 节的 router 冻结能稳定总体负载，却不保证每个 micro-batch 都没有极端峰值。
* **扩容和减少冗余之后，仍要管理局部上限。** 分布式存储与打包减少了中央瓶颈，但长序列仍可能集中在某个节点。持续观察单节点峰值、并为其设置容量约束，比仅监控总内存使用更能暴露这类风险。

**这一节最有价值的结论是：系统必须适应训练过程中的负载变化。** 策略生成长度、harness 组合和启动状态都会影响资源需求，训练初期安全的配置不一定能持续运行到后期。因此，第 2 节的总运行时间包含故障与恢复，不能直接当成稳定状态下的训练速度。

## 10. MOPD2：合并教师能力，并覆盖难以可靠评分的任务

来源：§5.6、Figure 13；教师评分的系统实现见 §6.2。

**Mixed RL 之后，MiMo 用多个领域教师继续监督学生模型。** 这一步称为 Multi-Prefix Multi-Teacher On-Policy Distillation（多前缀、多教师在线策略蒸馏，MOPD2）：既合并 RL 教师的能力，也利用 SFT 教师拓展难以直接做 RL 的领域。

### 10.1 从任务奖励切换到教师监督

教师有两类来源：**可验证任务用 MixRL 训练领域教师，开放任务用高质量合成示范训练 SFT 教师。** 前面的代码、工具使用、视觉等任务已经参与混合 RL；后续蒸馏并非只用于新任务，也承担能力合并。报告列举的拓展方向包括长周期游戏开发、科学研究与具身智能，但未分别量化增益。

关键变化在学习信号：RL 依据任务结果与质量评价更新；OPD 则让学生自己生成内容，再接受教师的逐 token 监督。系统中，奖励评价被教师评分替代；报告未说明在此阶段继续混合 GRPO loss，也未完整披露教师名单与学生初始化细节。

> **Insight：难以写出可靠奖励，不代表无法提供训练监督。** 教师可以利用示范中学到的能力指导学生，但这把监督质量的依赖从验证器部分转移到了教师。蒸馏拓宽了可训练任务范围，并不保证教师在所有学生状态下都能给出可靠指导。

### 10.2 三条路径：完整执行，或从已有历史开始生成一轮

| 路径 | 学生如何生成 | 教师如何监督 |
| --- | --- | --- |
| Standard MOPD | 从任务起点自主完成整条轨迹 | 适用领域的 MixRL 教师逐 token 指导 |
| Teacher-Prefix OPD | 从教师轨迹中某轮之前的完整历史出发，生成新一轮 | 对应领域教师基于相同历史和学生已生成内容指导 |
| SFT-Prefix OPD | 从 SFT 示范中某轮之前的完整历史出发，生成新一轮 | 对应领域教师基于相同历史和学生已生成内容指导 |

一条源轨迹有 $`k`$ 个 assistant turns，就可提取 $`k`$ 个完整历史前缀 $`h_1,\ldots,h_k`$，分别作为学生生成的起点：

```math
y_i\sim\pi_{\mathrm{student}}(\cdot\mid h_i),\qquad i=1,\ldots,k.
```

**示范提供上下文，不提供必须照抄的下一轮答案。** 例如，从“已读完仓库、准备修改代码”的历史开始，学生自己生成修改操作，教师监督这次新生成；无需让学生重新执行前面的阅读过程。这是解释性例子，不是报告中的具体任务。

### 10.3 前缀的作用：减少长交互累积偏离，保持教师监督有效

SFT 教师主要从高质量示范学习。学生连续自主执行后，可能进入示范很少覆盖的错误状态，教师未必擅长在这种历史下指导。**从示范或教师轨迹的前缀出发，可以减少生成本轮之前的累计偏离**，同时复用已有历史，省去重复执行。

> **Insight：Prefix OPD 既是在复用数据，也是在选择教师更容易有效指导的上下文。** 学生的新一轮由当前策略生成，但前面的历史来自外部轨迹。因此，它能训练模型在这些状态下如何继续，却不能单独证明模型能自主到达这些状态、或从自己的错误中恢复；后者仍需完整 rollout 评测。

最终成绩应理解为 **RL 与后续蒸馏共同作用的结果**。报告未给出足够细节确定蒸馏损失的 KL 方向或全词表实现，也不能把 DeepSeek V4 的教师与缓存配置直接套用到这里。

## 11. 实验解读：区分训练收益、最终能力与小模型验证

**三类结果回答不同问题。** RL 曲线反映训练过程中怎样变化，最终模型表反映完整训练链路后的能力，9B 实验则检验蒸馏底座与领域 RL 的效果。不能将它们拼成一条连续的性能曲线。

### 11.1 RL 曲线：成绩与解题资源使用同时变化

来源：Figures 3、9–10。

DeepSWE average@3：Pro **58.4 → 72.6**，Flash **48.7 → 65.7**，分别提升 14.2、17.0 个百分点。average@3 是三次尝试成绩的平均，不是三次中至少成功一次的 pass@3。

代码、通用工作流与视觉任务的成绩都在改善，但评测 token 使用也总体增长。**这支持该训练流程能提高成功率，尚不能分离“策略更有效”与“投入更多解题计算”的贡献。** 判断效率仍需比较相同解题预算下的成绩，见第 2 节。

在三个未见框架 Codex、Claude Code、mini-swe-agent 上，DeepSWE 平均 Pass@1 约从 **50% 到 66%**，支持能力迁移。缺少计算与数据匹配的单框架对照，不能据此单独归因多框架训练的收益。同样，这些曲线也不足以确定最优 batch 或外推更长训练的收益。

**RL 列来自各领域分别训练的检查点，不是同一个 9B 模型同时达到全部成绩。** 它们从共同 SFT 起点出发，其中代码实验使用单框架训练。

> **Insight：SFT 与 RL 的相对贡献随任务变化。** AutomationBench 先由 SFT 从 5.0 提升到 30.3，再由 RL 到 33.1；Terminal Bench 2.1 的 RL 增量则是 37.1 到 52.8。前者说明高质量示范已提供大量能力，后者说明这个 SFT 起点仍有较大的 RL 改善空间。这不能进一步证明某类任务普遍更适合 SFT 或 RL。

另一个独立的多框架代码实验（Table 7）在七种框架上，不加权平均成绩分别为：SWE-bench Verified **62.3 → 65.7**、SWE-bench Pro **44.4 → 46.5**、MiMo Code Bench mini **53.1 → 59.0**，全部 21 个数据集—框架组合均提升。它补充了跨框架改善的证据，但不能与上表拼成同一个连续实验。
